# 6色思考会議

Chrome Built-in AI（Prompt API / Gemini Nano）を使い、シックスハット法で意思決定を整理するローカルWebアプリです。

## 起動

1. リポジトリをダウンロードまたはクローンします。
2. Chromeで `index.html` を開きます。
3. 画面上部が「モデル準備完了」になることを確認します。

開発者向けテストハーネスは、URL末尾に `?dev=1` を付けて開きます。

```text
index.html?dev=1
```

環境によって直接ファイルを開けない場合は、任意の静的HTTPサーバーから配信してください。

```bash
python -m http.server 8000
```

## v1.3.0 / Schema 4 Lite

Schema 4 Liteでは、Gemini Nanoへ渡す最終判断の仕事を小さくしました。

1. 緑の帽子は標準実行でcompact Schemaを使い、構造の異なる政策・実施方式を3案生成します。
2. 「深掘り」を明示した場合だけnormal Schemaで4案を生成します。normalが失敗した場合はcompactへ戻します。
3. 各案について「含める・条件付き・除外」をユーザーが確定します。
4. 最終青へ渡す候補は最大3案です。
5. 除外案、組合せメモ、黒の対応策、黄の戦略的機会、赤の関係者別結果は最終青へ渡しません。
6. Gemini Nanoは候補の比較、選択、短い理由、事前に用意されたアクションIDの選択だけを行います。
7. 案名、案の概要、アクション本文、最終表示はJavaScriptが元データから組み立てます。

緑では、案本体と検証方法を分離します。案本体は段階導入、地域限定、共同実施、外部委託、工程変更などの政策・実施方式とし、`pilotMethod`にだけヒアリング、机上確認、試験搬入、小規模実証などの検証行動を書きます。「机上確認」「試験搬入」など検証手順だけの案名や、categoryが十分に分かれていない案群は意味検証で再生成します。

制約は各案について全件を`satisfies`・`violates`・`unknown`で評価します。対象外事項は問題があるIDだけを返すconcern-only形式です。対象外事項についてモデルから懸念が返らなかった場合は`no_concern_reported`として保存しますが、それだけで候補を条件付きにはせず、情報充足度も減点しません。

`pilotMethod`には、契約、発注、設備購入、全面導入ではなく、中止・見直し可能な検証行動を求めます。不可逆な文言が返った場合、最終青へ渡すアクションはJavaScriptが可逆的な確認行動へ置き換えます。

これにより、除外した案が言い換えられて最終推奨へ戻ること、選択案と表示名・出典がずれること、条件付き判断なのに契約締結などへ直行することを抑えます。

## 主な特徴

- 7段階の帽子別分析
- JSON Schemaによる構造化出力
- 非ストリーミングの処理フェーズ・経過時間表示
- 帽子単位の自動保存と中断再開
- 緑は標準3案、深掘り時のみ4案
- 緑の生成は6分でタイムアウトし、compactで最大1回再試行
- 失敗・中止attemptにも実時間、Prompt長、コンテキスト測定値を保存
- 緑案の採否確認UI
- 最大3案の軽量な最終比較
- 各最終候補へ最低1件の可逆的アクション候補を確保
- 最終青のコンテキスト使用量を事前測定
- 制約・対象外事項の追跡
- 重大度別の警告制御
- 表示・生成テストとPASS／FAILレポート

## 保存データ

v1.3.0はSchema 4専用の保存領域を使用します。

```text
sixHatsMeetingsV4
```

Schema 3以前のJSONは自動移行しません。旧保存データは削除せず、v1.3.0からは読み込みません。

## 静的チェック

Node.js 20以降で実行できます。外部パッケージは不要です。

```bash
npm test
```

静的チェックには、次の回帰テストを含みます。

- 制約違反案が初期状態で除外される
- 明示的な制約`unknown`が条件付きになる
- 対象外事項の懸念未申告だけでは条件付きにならない
- 検証手順だけの緑案名を拒否する実装がある
- compactの緑案に3種類以上のcategoryを要求する
- 除外案が最終青コンテキストへ入らない
- 黒の対応策と黄の戦略的機会が最終青へ流入しない
- normal／compactの全候補にアクション候補が存在する
- 契約・全面導入など不可逆なアクションを最終青へ渡さない
- 案別評価に別候補の案名が混入した場合は拒否する
- 選択案IDとアクションIDの整合性を検証する
- 最終表示を元の緑案から決定論的に組み立てる
